## 1. 目的

本文件說明「文件倉儲管理系統 2.0」專案文件的統一存放位置、目錄結構、命名規範與使用方式，確保所有專案文件（除程式碼外）集中管理，提升文件的可維護性與可追溯性。

---

## 2. 範圍

本文件涵蓋：
- 專案文件的統一存放位置規範
- `docs/` 目錄結構說明
- 各子目錄的用途與命名規範
- 新增文件時的放置位置指引
- 文件路徑引用規範

**適用對象**：
- 專案開發人員
- 專案管理人員
- AI Assistant（需遵循此規範建立與更新文件）

---

## 3. 權責

### 3.1 專案負責人
- 核准文件目錄結構變更
- 確保所有文件遵循統一存放規範

### 3.2 開發人員
- 新增文件時，必須放置於 `docs/` 下對應的子目錄
- 引用其他文件時，必須使用 `docs/` 為起點的相對路徑

### 3.3 AI Assistant
- 建立新文件時，必須遵循本規範
- 更新文件時，必須同步修正路徑引用（若引用舊路徑）

---

## 4. 名詞解釋

- **docs/**: 專案根目錄下的文件集中存放資料夾，為所有非程式碼文件的唯一存放位置
- **SDD 文件**: 遵循「規格驅動開發 (SDD) 工作流程」產出的文件，包含 spec.md, plan.md, tasks.md, review.md
- **標準文件**: 專案憲章、總規範、SDD 工作流程等不可隨意更動的基礎文件
- **相對路徑**: 以 `docs/` 為起點的檔案路徑（例如：`docs/0.standards/...`）

## 5. 作業內容

### 5.1 統一存放位置規範

**核心原則**：除程式碼以外之專案文件**一律**集中存放於專案根目錄下的 `docs/` 資料夾。

**禁止事項**：
- ❌ 將文件散落於專案根目錄（如 `0.standards/`、`1.specs/`、`2.plans/`…）
- ❌ 將文件存放於其他非 `docs/` 路徑

**例外情況**：
- ✅ 專案根目錄 `README.md`（專案總覽）
- ✅ 子專案 `frontend/README.md`、`backend/README.md`（子專案說明）

### 5.2 標準目錄結構

`docs/` 下必須維持以下固定結構（不可任意改名）：

```
docs/
├── 0.standards/     # 標準文件：專案憲章、總規範、SDD 工作流程等（不可隨意更動）
├── 1.specs/         # 規格文件 (SPEC)
├── 2.plans/         # 計畫文件 (PLAN)
├── 3.tasks/         # 任務文件 (TASKS)
├── 4.reviews/       # 審查/驗收文件 (REVIEW)
├── 5.otherDocs/     # 其他文件：初始化說明、會議記錄、探索文件等
└── README.md        # 本文件（docs 文件總覽與使用說明）
```

### 5.3 各子目錄用途說明

#### 5.3.1 `0.standards/` - 標準文件

**用途**：存放專案基礎規範文件，這些文件定義了專案的核心原則與標準，**不可隨意更動**。

**包含內容**：
- 專案憲章 (Project Constitution)
- 設計規範 (Design Standards)
- SDD 工作流程 (SDD Workflow)
- 資料庫結構分析文件
- 其他標準規範文件

**子目錄結構範例**：
```
0.standards/
├── 0.專案憲章-總規範-SDD工作流程/
│   ├── 1.專案憲章 Project Constitution.md
│   ├── 2.文件倉儲管理系統 Warehouse Management System 設計規範v2.0.md
│   └── 3.規格驅動開發 (SDD) 工作流程.md
├── 4.資料庫結構分析/
│   ├── 1.基本作業/
│   ├── 8.系統管理作業/
│   └── ...
└── README.md
```

#### 5.3.2 `1.specs/` - 規格文件 (SPEC)

**用途**：存放 Phase 1 產出的規格文件，定義「做什麼」。

**檔案命名規範**：`[模組名稱].spec.md`

**子目錄結構**：
- 必須依據 **8大核心功能** 分類存放
- 共用或特殊模組（如：登入作業）可直接置於 `1.specs/` 根目錄

**範例**：
```
1.specs/
├── 1.基本作業/
│   ├── 1.1.代碼維護.spec.md
│   └── 1.3.客戶資料維護/
│       └── 客戶聯絡人異動API.spec.md
├── 8.系統管理作業/
│   └── 8.1.身分識別與權限管理/
│       ├── IAM基礎API.spec.md
│       └── 資料遷移Migration.spec.md
├── 1.登入作業.spec.md
└── README.md
```

#### 5.3.3 `2.plans/` - 計畫文件 (PLAN)

**用途**：存放 Phase 2 產出的計畫文件，定義「怎麼做」。

**檔案命名規範**：`[模組名稱].plan.md`

**子目錄結構**：與 `1.specs/` 相同，依據 8大核心功能分類

**範例**：
```
2.plans/
├── 1.基本作業/
│   ├── 1.1.代碼維護.plan.md
│   └── 1.3.客戶資料維護/
│       └── 客戶聯絡人異動介面.plan.md
├── 8.系統管理作業/
│   └── 8.1.身分識別與權限管理/
│       └── 資料遷移Migration.plan.md
└── README.md
```

#### 5.3.4 `3.tasks/` - 任務文件 (TASKS)

**用途**：存放 Phase 3 產出的任務文件，將計畫拆解為可執行的任務清單。

**檔案命名規範**：`[模組名稱].tasks.md` 或 `[模組名稱].Tasks.md`

**子目錄結構**：與 `1.specs/` 相同

#### 5.3.5 `4.reviews/` - 審查/驗收文件 (REVIEW)

**用途**：存放 Phase 5 產出的驗收文件，記錄驗收結果與測試報告。

**檔案命名規範**：`[模組名稱].review.md` 或 `[模組名稱].REVIEW.md`

**子目錄結構**：與 `1.specs/` 相同

#### 5.3.6 `5.otherDocs/` - 其他文件

**用途**：存放不屬於 SDD 流程的其他文件。

**包含內容**：
- 專案初始化說明
- 會議記錄
- 探索性文件
- 技術研究文件
- 聊天記錄（若需保存）

**子目錄結構**：可依需求自行組織

**範例**：
```
5.otherDocs/
├── 專案初始化說明.md
├── Samba_AD_DC架設/
│   └── Ubuntu Server 上 Samba AD DC 架設紀錄.md
└── chat_history/
    └── README.md
```

### 5.4 新增文件時的放置位置指引

#### 5.4.1 新增 SPEC 文件

**情境**：要為「客戶資料維護」模組建立規格文件

**正確路徑**：
```
docs/1.specs/1.基本作業/1.3.客戶資料維護/[模組名稱].spec.md
```

**步驟**：
1. 確認功能分類（「客戶資料維護」屬於「1.基本作業」）
2. 確認子功能編號（1.3）
3. 在對應路徑建立文件

#### 5.4.2 新增 PLAN 文件

**情境**：要為「客戶聯絡人異動介面」建立計畫文件

**正確路徑**：
```
docs/2.plans/1.基本作業/1.3.客戶資料維護/客戶聯絡人異動介面.plan.md
```

**注意**：PLAN 文件的路徑結構應與對應的 SPEC 文件保持一致

#### 5.4.3 新增其他文件

**情境**：要記錄一次技術討論會議

**正確路徑**：
```
docs/5.otherDocs/技術討論/2026-01-01-技術討論記錄.md
```

**建議**：在 `5.otherDocs/` 下建立有意義的子目錄分類

### 5.5 文件路徑引用規範

**核心原則**：所有文件內引用（Markdown link）**必須**以 `docs/` 為起點撰寫相對路徑。

**正確範例**：
```markdown
- 參考文件：`docs/0.standards/0.專案憲章-總規範-SDD工作流程/1.專案憲章 Project Constitution.md`
- 依據：`docs/1.specs/1.基本作業/1.3.客戶資料維護/客戶聯絡人異動API.spec.md`
```

**錯誤範例**：
```markdown
❌ `0.standards/0.專案憲章-總規範-SDD工作流程/1.專案憲章 Project Constitution.md`
❌ `1.specs/1.基本作業/1.3.客戶資料維護/客戶聯絡人異動API.spec.md`
```

**原因**：使用 `docs/` 為起點可避免未來移動造成斷鏈，確保路徑一致性。

## 7. 使用表單

### 7.1 新增文件檢核表

新增文件前，請確認以下項目：

- [ ] **確認文件類型**：SPEC / PLAN / TASKS / REVIEW / 其他
- [ ] **確認功能分類**：屬於 8 大核心功能的哪一項？
- [ ] **確認子功能編號**：如 1.1, 1.3, 8.1 等
- [ ] **確認檔案命名**：是否符合命名規範（`[模組名稱].[類型].md`）？
- [ ] **確認存放路徑**：是否放置於 `docs/[對應目錄]/` 下？
- [ ] **確認路徑引用**：文件內所有引用是否以 `docs/` 為起點？

### 7.2 文件路徑引用檢核表

更新文件時，請檢查以下項目：

- [ ] **檢查所有 Markdown 連結**：是否以 `docs/` 為起點？
- [ ] **檢查相對路徑**：是否正確指向目標文件？
- [ ] **檢查舊路徑引用**：若有引用舊路徑（非 `docs/`），是否已修正？
